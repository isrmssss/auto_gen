# future — очередь гипотез

Файлы здесь = ещё не протестировано. Формат: `NNN_slug.md` или `hxx_slug.md`.

**Сначала** brief в [`../investigate/`](../investigate/), **потом** гипотеза здесь. Без исследования — не ставить в очередь.

После каждого цикла агент **доводит очередь до N=`workers`** по квотам портфеля (см. [`AGENTS.md`](../../AGENTS.md) → «Формирование гипотез»). Не оставлять один refine.

## Типы

| Тип | Смысл |
|-----|--------|
| **refine** | Тот же механизм, 1–2 параметра / узкий guard |
| **pivot** | Та же цель KPI, другой механизм |
| **explore** | Другая ось пайплайна / архитектуры / данных |
| **validate** | Holdout/repro; не занимает слот refine |

## Шаблон

Каждая гипотеза — **короткий, но законченный текст**: читатель без контекста цикла должен понять *что меняем*, *как это работает*, *почему ждём эффект* и *чем рискуем*. Не телеграфные тезисы, а связный абзац.

**Объём:** поля **Идея** и **Почему** — по **3–5 предложений** каждое. Метаданные (Тип, Линия) — одна строка. Весь файл обычно **≤350 слов**.

**Стиль:**
- нормальные информативные фразы, не список ключевых слов;
- явно: baseline → **условие триггера** → действие → что **не** меняем (guardrails проекта) → ожидаемый эффект на KPI из METRICS;
- **Почему** = причинно-следственная цепочка из brief/past/analytics, не «проверим гипотезу»;
- без id кейсов и regex под один split; категории/срезы — обобщённо.

**Запрещено:**
- «чуть снизить X», «тот же механизм + N%», «ещё чуть подкрутить»;
- жаргон-only без условия как единственная «Идея»;
- копипаста строки из таблицы кандидатов brief без разворота в 3–5 предложений.

**Чеклист перед записью в очередь:**
1. В **Идея** есть конкретный baseline (Hx / arm / конфиг) и когда срабатывает правило.
2. Написано, что остаётся без изменений (safety / hard-constraint проекта).
3. **Почему** ссылается на цифру из investigate/analytics/past, не на ощущение.
4. Главный риск регрессии по hard-constraint и как дизайн его ограничивает — одним предложением.

```markdown
# NNN — короткое имя

**Тип:** refine | pivot | explore | validate
**Линия:** Hx / new
**Исследование:** [`../investigate/NNN_slug.md`](../investigate/NNN_slug.md) — какой вопрос из brief закрывает эта гипотеза

**Идея:**  
Связный абзац: от какого baseline отталкиваемся; что именно меняется; при каком условии срабатывает; что остаётся без изменений. Ожидаемый эффект на KPI — одним предложением.

**Почему:**  
Связный абзац: какие наблюдения из investigate/past наталкивают на этот механизм; почему предыдущие попытки не подошли; главный риск и как его ограничиваем.

**Acceptance:** по `config.yaml` / METRICS.md vs `baselines.champion` (и control при наличии); holdout при ⚠️/✅ если включено.

**Избегать:** опровергнутые линии (`banned_lines`, cemetery), hardcode id, regex под конкретный прогон
```

## Квоты портфеля

- Минимум 1× `pivot` или `explore`.
- Максимум 1× `refine` от одной линии.
- Не больше 2 подряд refine одной линии в `past/` → дальше только pivot/explore по этой линии.
- Типично при N=3: `refine + pivot + explore` (или `validate + pivot + explore`).

## Анти-переобучение

- Не формулировать гипотезу как «исправить категорию X на split Y».
- Не использовать golden id для **обучения** правил — только holdout-check.
- После ⚠️/✅ — holdout на сплитах из `config.yaml` → `holdout_splits`.

После прогона файл **удалить** (отчёт в `past/`).
